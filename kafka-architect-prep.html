Kafka Architect Interview Prep

Whiteboard-ready preparation for designing high-scale, multi-tenant streaming platforms — with a focus on the 100M events/sec problem, noisy neighbors, quotas, isolation, burst handling, reliability, DR, and trade-offs.

1. The interview problem

Prompt: Design a Kafka-based platform that can support 100M events/sec. Multiple tenants produce events and have downstream consumers. One tenant suddenly has a huge traffic burst. How do you prevent a noisy neighbor from affecting everyone else? Would you re-architect any components?
Architect mindset: Do not jump straight to “add brokers.” Treat this as a platform problem involving capacity, admission control, tenant isolation, buffering, downstream protection, and a control plane.

2. Start with the capacity math

100M/s
Peak event rate
~100 GB/s
Logical ingress at 1 KB/event
~8.64 PB/day
Raw logical data/day
~25.9 PB/day
RF=3 physical copy volume/day, before compression/overhead
100M events/s × 1 KB ≈ 100 GB/s
100 GB/s × 86,400 ≈ 8.64 PB/day
8.64 PB/day × RF(3) ≈ 25.9 PB/day
Interview point: Kafka should usually be your hot, replayable event backbone—not your cheapest long-term archive. Think Kafka + object storage/data lake.

                    |

             Control Plane
                    |
          +---------+---------+
          |                   |
     short-lived          sustained
          |                   |
       drain burst         promote / isolate

Short burst

Use quotas, backpressure, and buffering. Do not immediately migrate infrastructure for every spike.

Sustained high-volume tenant

Use policy-driven promotion to dedicated topics/partition pools or a dedicated Kafka cluster. This is an architectural isolation decision, not just autoscaling.

Important: A buffer absorbs a burst; it does not create capacity. If ingress is 10 GB/s and the sustainable drain rate is 2 GB/s, backlog grows at 8 GB/s until the burst ends or capacity increases.

6. Kafka quotas

Kafka supports client quotas for protecting shared clusters from high-volume clients. Use them as a first line of defense.

Tenant A → 500 MB/s producer quota
Tenant B → 200 MB/s producer quota
Tenant C →   1 GB/s producer quota
Don't overclaim: Quotas protect shared broker resources. They do not by themselves solve business-aware burst absorption, downstream overload, or automatic tenant promotion.

7. Partitioning and ordering

partition = hash(customerId) % N

This gives ordering per customer key while permitting parallel processing across customers.

Hot key trade-off: If one customer generates enormous traffic, strict ordering can pin that customer to one partition. Sharding the customer can restore horizontal scalability but changes the ordering semantics.

8. Partition sizing methodology

Do not quote a universal Kafka partition throughput number. Benchmark your actual workload.

Required partitions ≈ total throughput / sustainable throughput per partition

Illustrative example: if a production-equivalent benchmark establishes 25 MB/s as the sustainable partition target:

100 GB/s / 25 MB/s ≈ 4,000 partitions

Then add headroom, account for uneven partitioning and validate recovery behavior. Exact production sizing should be benchmark-driven.

9. Broker sizing

Size against the limiting resource rather than one throughput number:

Broker fleet size = max(network, disk, CPU requirements)
                   × replication / recovery headroom

Benchmark under peak traffic, RF=3, normal consumer traffic, and broker/AZ failures. A cluster that works at 95% utilization in steady state may not have enough capacity to recover from failure.

Protect downstream dependencies too. Autoscaling consumers without considering database/API capacity can simply move the outage downstream.

Kafka → Consumer → Bulkhead / Rate Limit → DB / Search / API

11. Failure scenarios

Broker failure
Replica becomes leader when appropriate; clients reconnect. Recovery consumes disk/network capacity, so recovery capacity must be part of planning.
Availability-zone failure
Replicas should be spread across failure domains. Surviving brokers must have enough spare capacity to absorb the load.
Consumer crash after DB commit
The event can be processed again. Use stable event IDs and idempotent business processing; do not assume Kafka offsets eliminate duplicates.
Poison message
Route repeatedly failing records to a DLQ with topic, partition, offset, event ID, error, schema version, and original payload so the message can be diagnosed and replayed safely.
Downstream DB is slower than Kafka
Use Kafka or another durable queue as a buffer between stages, but monitor backlog and retention so the buffer does not silently exhaust.

12. Multi-region DR

          US Kafka  ===== async =====>  EU Kafka
              ^                           |
              |                           v
          EU Kafka  ===== async =====>  US Kafka

For a one-minute RPO, monitor cross-region replication lag continuously. Don't claim a zero-RPO design unless the architecture actually provides it.

Use regional ingestion to avoid unnecessary WAN traffic. Replicate only the data that actually requires cross-region recovery; replicating everything everywhere can multiply storage and network cost.

13. Schema governance

Producer → Schema Registry / Compatibility Check → Kafka → Consumer

Every event should carry an event ID, event type, schema version, event time, and tracing context where appropriate.

14. Replay strategy

Kafka
  ├── Production Consumer Group
  └── Replay Consumer Group

Use separate consumer groups for replay. Be especially careful when replaying side effects such as payments, notifications, or shipping actions.

This separation is one of the strongest architectural ideas in the problem. The control plane decides how the data plane should behave; it does not process the event stream itself.

16. What not to do

Don't:
Give every tenant a dedicated Kafka cluster by default.
Don't:
Assume adding brokers instantly solves a short-lived burst.
Don't:
Use global ordering as the default requirement.
Don't:
Autoscale consumers without protecting downstream systems.
Don't:
Claim exactly-once for external side effects without business-level idempotency.
Don't:
Size the cluster at 90–100% steady-state utilization.

17. Interview follow-up drill

Why Kafka quotas instead of a gateway?
Use both when useful. Kafka quotas protect broker resources; a gateway can enforce business-aware policies, prioritize events, perform tenant-aware routing, and expose tenant-specific admission control.
Why multiple clusters?
To reduce blast radius, isolate noisy tenants, simplify operations, and allow independent capacity and lifecycle management.
How many partitions?
Derive from measured sustainable partition throughput, then add headroom and validate failure/recovery behavior. Never present a theoretical number as a production guarantee.
How do you handle a single hot customer?
Either preserve strict ordering on one partition and accept the ceiling, or shard the key and introduce downstream logic to restore only the ordering semantics the business actually needs.
Why not exactly-once everywhere?
Exactly-once is valuable for selected workflows but can add complexity and coordination. A common platform default is at-least-once transport plus idempotent processing, with stronger guarantees where required.
What if the burst exceeds every buffer?
Define explicit policy: throttle, backpressure, prioritize critical events, spill to durable storage when appropriate, or reject best-effort traffic. No system can provide infinite buffering.
How do you know when to promote a tenant?
Use sustained ingress rate, throttle time, partition hotness, consumer lag, cluster utilization, SLA class, and duration thresholds—not a single instantaneous spike.
How do you protect the database?
Bound concurrency, rate-limit, batch, bulkhead, and keep Kafka as a durable buffer. Consumer autoscaling must respect downstream capacity.

18. The 2-minute architect answer

“I would treat this as a noisy-neighbor and burst-management problem rather than simply a Kafka scaling problem. I would introduce tenant-aware admission control plus Kafka client quotas to prevent any tenant from monopolizing broker resources. I would use a tiered tenancy model: smaller predictable tenants share clusters, while high-volume or highly bursty tenants can be isolated onto dedicated topic/partition pools or clusters.

For short bursts, I would use backpressure and buffering; for sustained abnormal volume, the control plane can promote the tenant to isolated capacity. I would also isolate consumer compute and protect downstream databases and APIs because otherwise the tenant can simply move the overload downstream.

Partitioning would be by business key to guarantee per-key ordering, with an explicit strategy for hot keys. Kafka would provide hot retention and replay, while object storage would hold long-term history. Multi-region DR would use regional Kafka clusters with asynchronous replication for selected critical topics, measured against the required RPO.

The result is a platform that is shared by default, protected by quotas, tolerant of bursts, and able to isolate tenants when their workload justifies it.”
